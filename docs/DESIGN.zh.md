# 设计说明

**中文** · [English](DESIGN.md)

为什么 `dsh-pet-progress` 是这样写的。[README](../README.zh.md) 讲怎么用这个
插件；这份文档讲怎么改它。

## 它填补的缺口

宠物本来就有丰富的**瞬时活动**词汇：

```
'idle' | 'waiting' | 'thinking' | 'tool' | 'review' | 'done' | 'failed'
```

这七个都在描述「此刻」。没有一个能表达*「7 个任务做完了 3 个」*，所以一个长任务
刚开始和快做完看起来一模一样；而当 agent 在两步之间安静下来时，宠物会退回
`idle`，哪怕还有一大堆活没干。

持久的进度其实就存在于会话日志里。DSH 把它记成 `todo/write` 和 `goal/change`
事件，但宠物的事件投影只对 `turn/start`、`step/start`、`assistant/message`、
`tool/call`、`tool/result`、`turn/end` 做分支——其余一律返回 `undefined`，被丢掉：

```ts
// 宠物 event-projection.ts 的真实行为
default:
  return undefined
```

所以这些信息一直有人在写，只是没人读。

## 为什么是兄弟插件，而不是打补丁

宠物的源码一行都不改，因为它是 npm 依赖，将来一次 `dsh plugin add` 就会把它覆盖
掉。这个插件改用宠物和 harness 已经公开的扩展点：

| 缝 | 用途 |
| --- | --- |
| `ctx.on('session/event', …)` | 读 `todo/write` + `goal/change`，在 `turn/end` 退休，在 `turn/start` 重放；同一条通道也承载活动行背后的 turn/step/tool/message 事件——宠物也在监听它，所以双方都看得到每一个持久事件 |
| `ctx.on('agent/assistant-stream', …)` | 活动行要的实时模型输出，从 `text-delta` chunk 里取。它是进程内发布而不是会话事件，所以会话要从 `agent.session.id` 拿 |
| `ctx.pet.announce(…)` | 把进度气泡投进宠物已有的公告栈 |
| `ctx.pet.registerPanelAction(…)` | 一个 `进度` 按钮，打印完整 todo 列表，因为气泡只有一行 |

有数值的气泡用 `kind: 'plan'` 发布，直接复用宠物现成的百分比条渲染；没有数值的
概要则改走 `cost`（见下文[当没有东西可计量时](#当没有东西可计量时)）。不需要客户端
bundle——这个插件是纯宿主的。

这两个契约都是进程内的，且由宠物自己限定范围，所以这个插件出 bug 最坏也只是气泡
静默不显示，不会弄坏宠物。这里不会往会话日志或宠物的持久状态里写任何东西。

## 它汇报什么

优先级从高到低：

1. **被阻塞的目标压过一切**，直接显示人类可读的原因——一个卡住的任务是唯一值得
   打断的事。
2. **有 todo 列表**时显示百分比条加 `completed/total`，标题是当前 `in_progress`
   的那个任务——有多个在跑时，就把它们都点名（最多三个，其余 `+N`），因为
   「这几个里到底哪个是当前的活」正是多任务列表最容易产生的疑问。
3. **有目标但没有 todo**时退回目标的轮次预算，例如 `2/8 轮`。
4. **既没有 todo 列表也没有目标**时，一行纯活动文字——没有百分比。见下一节。

两条关于可信度的硬规则：

- **进度绝不虚报。** 无法识别的 todo 状态算作 `pending` 而不是 `completed`
  （`src/progress.ts` 里的 `readTodo` 把一切非 `completed`、非 `in_progress` 的值
  都当 `pending`），而一个所有条目都畸形的列表被当作*没有信息*，而不是*没有活
  干*。一次空的写入不会把已存在的气泡抹掉。
- **只有在命名无歧义时才点名任务。** 同时进行的多个任务被逐个点名，而不是被
  归并成一个，气泡绝不会挑一个出来当成*那个*任务。超过三个就不再点名、改用
  计数（`+2`），因为需要滚动的标题不是状态行。

气泡 30 秒后过期（`PROGRESS_TTL_MS`），并由心跳刷新，所以它能熬过安静期，而不是
模型一停止发事件就立刻消失。

## 当没有东西可计量时

百分比需要有东西可量，而大量会话从来不写 todo 列表——一次普通的问答回合没有任何
可数的东西。这类会话过去什么都不显示，只剩宠物自己的阶段词作为唯一信号。

退路是**一行纯活动文字**，它的来源按顺序有三个：模型此刻正在流式说出的内容
（`agent/assistant-stream` 的 `reasoning-delta` 和 `text-delta` chunk）、它刚调用的
工具是干什么的（`正在调用 pwsh：npm test`），最后才轮到宠物自己的阶段词
（`等待模型响应`……）。它**不带 `percent`**，不假装自己是一次计量。

之所以读实时流而不是持久的 `assistant/message`，是因为后者要等这一轮尝试结束才
落地——只靠它的话，恰好在用户盯着屏幕的那段时间里，这行字什么都不会说。这条发布
按结构解析（`src/index.ts` 里的 `readLiveDelta`），只取插件需要的字段
（`agent.session.id`、`frame.chunk.text`），绝不 import agent 那边的帧类型，所以
对面改形状时最坏也只是「没有实时行」，而不是监听器抛异常。

模型自己的两种话都显示：思考时的 `reasoning-delta`，开始写答案后的 `text-delta`。
它们是两句话，所以类型切换时缓冲区和限流窗口都要重置，而不是把「想法」拼到后面那句
「答案」上；两者各有自己的小字（`正在思考` / `最近输出`）。纯阶段行只是最后的兜底，
留给两边都还没说话的停顿。

而这一行需要的，恰恰是公告契约里*没有*的那个形状。宠物会校验每一个载荷：`plan`
必须有 `percent`，`balance` 和 `cost` 必须有 `amount`，其余一律让
`parseAnnouncement` 返回 `undefined`——然后宠物**默不作声**地丢掉它，所以这次失败
看起来和「一个气泡从未被发送」完全一样。因此概要改走 `cost`：这个形状的 `amount`
会被客户端原样渲染成气泡正文；而小字（`title`）用来标来源，因为那是一个无数值气泡
唯一保证拥有的文本。`src/progress.ts` 里的 `announcePayload` 在唯一一处从气泡推导
kind，所以宿主适配器和 `src/wire.test.ts` 不可能各说各话——wire 套件通过同一个函数
构造载荷，再拿宠物真实的校验器去验。

四条规则保证这一行既诚实又稳定：

- **只对没有东西可计量的会话生效。** 只要 todo 列表或目标还在，活动事件根本不会被
  折叠，所以一个忙碌的、有计量依据的回合不会为这条退路付出任何代价。只有当两者都
  没了，这一行才出现。
- **沉默好过套话。** 只有说了具体东西的阶段（`waiting`、`tool`）才会以纯阶段行的
  形式发布；`thinking` 和 `review` 会被压掉（`src/index.ts` 里的 `QUIET_PHASES`），
  这样气泡不会在同一句话的两个增量之间闪回 `正在思考`。模型自己的话永远发布。
- **工具调用要说清是干什么的。** `src/progress.ts` 里的 `toolHint` 按最具体的那个
  参数取值——先 `command`，再 `query`、`path`、`file_path`（只显示文件名）、`url`、
  `name`——`readActivity` 把它接在后面，于是得到 `正在调用 read：progress.ts` 而不是
  `正在调用工具`。这些参数是作为 JSON *文本*存下来的，所以按结构解析；畸形载荷退化
  成光秃秃的工具名，而完全没有可用名字的调用仍返回 `undefined`，因为上一行已经比那句
  通用替换说得更多。
- **这一行只是概要态。** 它不占任何值得重放的槽位，所以 `turn/end` 直接*删除*该
  会话条目，而不是把它泊车；下一个 `turn/start` 从干净状态开始——包括实时文本缓冲区，
  所以新回合绝不会以旧回合的话开头。下面那条「泊车视图」规则只适用于带 todo 的会话。

重绘是限流的：增量到达的速度远快于人读气泡的速度，所以 `src/index.ts` 最多每
`STREAM_PUBLISH_MS`（400 毫秒）重绘一次，缓冲区上限 `STREAM_BUFFER_MAX`（600）个
字符，而实际显示的只有缓冲区最新的 `ACTIVITY_TEXT_MAX`（120）个字符——尾巴才是说
「此刻在干什么」的那部分。

小字标来源：阶段行是 `当前过程`，模型的思考是 `正在思考`，它正在写的回答是 `最近输出`。
正文就是那一行本身。

## 显示状态不是永久的

**`turn/end` 让气泡退休，`turn/start` 把它带回来。** 给一件已经没人做的工作显示
百分比，比不显示更糟，所以一轮结束时插件丢掉气泡并停止刷新它，让它自然过期。

这件事重要，是因为宠物的公告契约没有撤回——`announce()` 只能*设置*一个槽位，只有
TTL 能让它过期——所以让气泡退休意味着*不再重新发布*它。哪怕再多刷新一次，也会重启
TTL，把一个已经结束回合的百分比永远留在屏幕上。

退休只到气泡为止，这是故意的。`todo/write` 只在 todo 列表**变化**时才发出，所以一个
不动列表的新回合什么都不发；如果退休时把折叠出来的视图也丢弃，插件在该会话第一次
回合结束后就会永久失声。因此视图被保留——除非它里面已经没有活的东西了，见下一节——
下一个 `turn/start` 从它重新发布。

### 已完成的列表是一次性提示，不是常态气泡

「永远钉在 `任务全部完成`」正是这条规则要防的事故。「`turn/start` 重新发布」这条对
还在进行的工作是对的，对已经结束的工作是错的：`completed === total` 的列表已经结束，
每来一个新回合就重播它一遍，会让一个*已完成*状态看起来像*当前*状态——在屏幕上，而且
是永久地。

所以渲染器区分两种气泡寿命：

- **常态**气泡（还有活没干完的百分比、还在推进的目标、活的活动行）由心跳刷新，一直
  活到回合结束；
- **一次性提示**（`任务全部完成`、`目标完成`）只发布**一次**，TTL 用
  `PROGRESS_MOMENT_TTL_MS`（10 秒），并且绝不存成该会话的常态气泡，所以心跳和下一个
  `turn/start` 都无法给它续命。

`src/progress.ts` 里的 `hasLiveProgress` 是这层区分背后的唯一判断：对已完成的列表和
已完成的目标返回 false，对被阻塞的目标返回 true（等人不算已经结束）。`src/index.ts`
在三处用它——`turn/start` 的重播保护、活动回退的闸门、`turn/end` 的退休——让这三处
对「什么才算还有活」保持一致。

让测量路径对一次性的提示不可达，也正是活动回退能重新接管的原因：列表一旦完成，会话
就没有东西可计量了，下一个事件会重新走进摘要路径，而不是重播一个 100% 的进度条。

## 两个不明显的细节

**挂载是延迟的，不是立即的。** 宠物在自己的 fiber 内部发布它的服务，所以一个兄弟行
可能在 `ctx.pet` 存在*之前*就被 apply。读一次 `ctx.pet` 然后返回，会让插件挂上又被
静默禁用整个启动周期，而且哪儿都不报错。因此当服务还没起来时，`apply()` 用
`ctx.inject(['pet'], …)` 等待。

**公告槽位没有撤回。** `announce()` 只能*设置*槽位，只有 TTL 能让它过期。这就是
为什么让气泡退休被实现为「停止刷新它」而不是「清空它」，也是为什么插件在回合结束后
绝不能重新发布。

## 状态与上限

投影里没有状态对象：每个事件都是**完整快照**（`todo/write` 带整张列表，
`goal/change` 带整个目标），所以折叠是 `(上一个视图, 事件)` 的纯函数，调用方只需持有
最后一个视图。这让整个功能不用 cordis 宿主就能测。

最多 `MAX_TRACKED_SESSIONS`（24）个会话保有独立的进度状态，超出时丢弃最久未触碰的。
最近一个带进度的事件占据唯一的公告槽位：用户看的是正在动的那个会话，而宠物的气泡栈
是一栏有限高度。它不会因为另一个不相关的会话变安静而被清掉，只会被另一个会话的带
进度事件顶掉。

## 构建

cordis 插件加载器**不做任何转译**，所以 `main` 必须指向纯 JavaScript。与其引入工具
链，`build.mjs` 用 Node 自带的 TypeScript 转译器——就是 `node file.ts` 背后那个——
并额外重写相对导入的说明符，因为转译器不做这件事。

`lib/` 是提交进仓库的，所以一次 clone 不需要构建就能加载。如果 `src/` 和 `lib/`
漂移，CI 会失败。
